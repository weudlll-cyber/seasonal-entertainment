## PIECE 2 — two small 2FA defects

Commit `c9c811e`, plus `7de2df8` (see "Found on the way"). PR #8 CI on `7de2df8`: green (run
39339488004, both jobs).

**a. A stored secret that decrypts but cannot be used answered 500.** Now refused like one
that does not decrypt.

- **How**: `openSecret` (server/src/twofa/secretBox.js) checks that the opened text is
  non-empty base32, through totp.js's own `base32Decode`. If not, it returns `null`, like a
  secret that does not open. Both callers (the login's `acceptSecondFactor` and
  `/2fa/enable`) were already refusing on `null`.
- **The answer**: the same as for a secret that does not decrypt, 401 `invalid_code` "That code
  is not valid.".
- **The log line**, in the same style: "[2fa] the 2FA secret of user <id> cannot be used: it
  decrypts, but not to a TOTP secret (encrypted twice, or the row was changed); this login is
  refused". No part of the secret is logged.
- **Test**: twoFactorAtRest.test.js seals the stored secret a second time (exactly what had
  happened to devadmin). The test checks for 401, the log line, no secret in the log, and that
  recovery codes still work.
  - Proven: with the check removed, the test is red with "expected 500 to be 401".

**b. `npm run dev:admin` keeps data/DEV-ADMIN.txt current.**

- When devadmin already has 2FA, the script reads the stored row (`getTwoFactor`), opens it
  (`openSecret`) and rewrites only the file's 2FA part: the secret and its otpauth link.
- The username and password lines are kept. Recovery codes are stored hashed, so the file says
  they are not shown again.
- It never calls setup, enable or reset. A secret that cannot be read leaves the file as it is.
- The file's 2FA text now comes from one function (`twoFactorPart`) for both the first setup
  and the rewrite.
- **Test**: devAdminScript.test.js puts a stale secret into the file and runs the script again.
  The test checks that the file holds the stored secret once, the password is kept, the
  "stored hashed" line is there, and the `two_factor` row is identical before and after.
  - Proven: with the old "nothing to do" back, the test is red.
- **Run once tonight** on the dev database (00:53).
  - The file had been written on 2026-10-17 at 02:30 and is now current.
  - Checked without printing any secret: the file's secret equals the stored one,
    devadmin's 2FA row is byte for byte unchanged, and the password line is kept.

**What was built**:

- **Server** (`server/src/bots/`):
  - **Reading** (`botDb.js`): each read opens the file with `{ readonly: true, fileMustExist:
true }` + `PRAGMA query_only` and closes it again.
  - **Cache**: 5 minutes per question, at most 200 keys, oldest out first. The visitor picks the
    week, so the keys would otherwise be unbounded.
  - **Routes** (`routes.js`), public and guests included:
    - `GET /api/prices`;
    - `GET /api/prices/:token?range=24h|7d|30d|1y|all`, at most 500 points. The range is cut
      into equal time slices, each keeping its last real snapshot; the latest price always
      stays.
    - `GET /api/bot-events?from&to`, a window of at most 8 days.
  - **Rate limit**: `makeLimiter` with `botRead` (120 a minute per address), behind `allow('public')`.
  - **Config**: `PRICE_BOT_DB` and `EVENT_BOT_DB` in `.env.example`. Unset: `connected: false`.
    An unreadable file answers 503 and logs why.
  - **Event safety**: a location URL is passed on only if it is http(s); `image_url` is never
    passed on.
- **Client**:
  - **Home card**: each season's price (four significant digits below a cent), its 24-hour
    change (green or red) and a sparkline. Without the bot: the season marks as before and
    "Prices: the data source is not connected."
  - **`/info/prices`**: under "Seasonal Tokens", with a link from `/info`. The info slug
    "prices" is now reserved on the server, so no info page can be hidden behind it.
    - A token picker with each token's price and change, and range buttons.
    - A hand-built SVG line chart in the season's colour token: the highest and lowest price,
      dated start and end times, and a hover or keyboard (←/→/Home/End) readout in local time.
    - No new dependency; the CSP is unchanged.
  - **`/events`**: the bot's occurrences of exactly the visible week, from local Monday to the
    next local Monday, so a daylight-saving week is right too.
    - Shown beside the site's own events. Same name (trimmed, any case) and same start minute:
      once, the bot's version.
    - A canceled occurrence is struck through with "canceled". Bot text is text only; a link
      gets `rel="noopener noreferrer"`.
    - The site's own event admin is unchanged.
- **Development data**:
  - `npm run dev:bot-fixtures` builds `data/bot-fixtures/snapshots.db` and `stannouncebot.db`
    (gitignored) with the bots' exact schemas and clearly fake, seeded data: a year of hourly
    prices; `[Sample]` events with one moved by two overrides, one canceled, one inactive, a
    non-web link, and a duplicate of a site event.
  - `npm run dev` points the two keys there when neither the shell nor `.env` sets them. An
    empty value keeps a bot off.
