**Answer: yes, it could miss its live update until reload**, in two ways. Both are held open
deterministically in client/src/chat/chatCatchUp.test.jsx, and both were red against the old
hook:

- (a) A message stored after the panel's load but before the server has taken the new socket's

### Part 2 — stale live calls

A call marked live whose LiveKit room no longer exists is ended by the site **10 minutes after
the room was first found missing**, exactly like "End call": status `ended`, call chat
read-only, audit `call.end` with actor **system**. The job checks at server start and then
every minute. It is off when `backgroundJobs` is off and when calls are not configured.

- **Design points**:
  - The time a room was first found missing is stored (`calls.room_missing_since`, added by
    `migrateCalls`), so a restart neither resets nor skips the grace period.
  - A room that comes back clears that time.
  - A call service that cannot be reached ends nothing (the check is skipped and logged).
  - The organiser's End route and the job share one function, `server/src/calls/endCall.js`,
    so they cannot drift apart. Two ends at once still succeed only once, via `markEnded`'s
    status guard.
- **Reused**: the chat retention job's pattern (run at start, `setInterval` with `unref`,
  gated by `config.backgroundJobs`), `markEnded`, `recordAudit` (actor `{ id: null, username:

### Part 3 — password key derivation off the main thread

Argon2id (`crypto_pwhash`, about 64 MiB, most of a second) now runs in a Web Worker for login,
registration, password change, unlock and recovery, and for every other password form too
(2FA setup and disable, admin password reset, creating a recovery code): they all go through
`session/credentials.js` or `keys/keyActions.js`. The buttons of login, registration,
password change, unlock and "Use recovery code" read **Checking…** while it runs.

- **How**:
  - `client/src/session/passwordHashing.worker.js` runs the very functions of
    `shared/crypto.js` (`deriveAccountKeys`, `deriveRecoveryKey`) and refuses anything else.
  - `passwordHashing.js` is the page's side, with the same signatures, one worker per page.
  - Without a `Worker`, or when it fails to load, the same functions run on the main thread.
  - Vite builds the worker as its own file (`/assets/passwordHashing.worker-*.js`,
    `worker.format: 'es'`).
- **CSP changes: none.** A same-origin module worker needs nothing new. The absent
  `worker-src` falls back to `script-src 'self'`, and the worker's response carries the same
  policy, whose existing `'wasm-unsafe-eval'` lets libsodium compile. Proven in real Chromium
  under the server's real headers by the new client/e2e/passwordWorker.spec.js.
- **Reused**: `shared/crypto.js` (unchanged), `mockApi`, the e2e seeded-member mechanism (one
  new member, `hashworker`), `FormMessage`.
- **Removed**: the main-thread `deriveAccountKeys`/`deriveRecoveryKey` calls in
  credentials.js and keyActions.js, and five hand-written submit buttons (now `BusyButton`).
- **Tests**: 8 new. Client: 6 in passwordHashing.test.js and 1 in busyButton.test.jsx.
  Browser: 1, passwordWorker.spec.js.
  - Worker results equal the main-thread results for a fixed password, recovery code and salt.
  - The page's side sends both derivations to one module worker of its own file on this
    origin, rejects with the worker's error, falls back once and stays there, and runs on the
    main thread without `Worker`.
  - The login button reads "Checking…", disabled and `aria-busy`, while the derivation is
    held in a stand-in worker.
  - A real login uses the worker, served from `/assets`, with no CSP violation.

  Sabotage: 7 runs, all red, then restored and green:
  - The worker derives something else.
  - The worker runs any operation.
  - The page side never uses the worker.
  - No fallback when the worker fails.
  - The worker's error is swallowed.
  - No busy label.
  - The CSP forbids workers (e2e; the login still worked through the fallback, the worker
    check went red).

  Full client suite: 217, all green.
