## Piece 1 — Security settings

### Chat connection limits

- **Limits**: at most 5 open chat connections per member account, counting every tab, the chat
  drawer and chats embedded on other sites together. Guests without an account get at most 20
  per address. Both are config keys with these defaults (`CHAT_MAX_CONNECTIONS_PER_MEMBER`,
  `CHAT_MAX_GUEST_CONNECTIONS_PER_IP`, in `.env.example`).
- **Refusal**: one more connection is accepted and closed at once with close code 4008
  (`TOO_MANY_CONNECTIONS`). A refused HTTP upgrade would look like a network error to the
  browser.
- **Message**: the chat area (room panel and direct-message panel) shows "You have the chat
  open in too many windows (at most 5). Close one and try again." with "Try again".
- **No retry loop**: the page tries again only when the reader presses "Try again", or when
  another tab of the same browser closes its connection (a `BroadcastChannel` message). An
  ordinary drop still reconnects after 3 seconds.
- **Address**: the one our own proxies forwarded, as Express's `req.ip` reads it with
  `TRUST_PROXY` hops (`clientIp`).
- **Counted by**: the hub (`countOpen`), which already knew every socket's session.
- **Reused**: `sessionUser` (who a session belongs to), `ChatNotice`'s classes, the
  `chat-link-button` style, the test helpers `listeningChat` / `connect` / `cookieOf`, and
  `FakeSocket`, which gained `closeByServer(code)`.

### Sessions: 7 days without use

- **Expiry**: a signed-in session ends after 7 days without use.
- **Renewal**: every authenticated request renews it to 7 days from then, at most once a minute
  (`renewSession`: the `usedAt` stamp, the cookie's and the stored expiry). The store's own
  per-request "touch" write is switched off.
- **Refusal**: a session whose `usedAt` is over 7 days old is refused (`sessionUser`, so the
  chat socket too).
- **Existing sessions**: signed-in sessions from the 30-day rule are capped at 7 days from the
  server's start.
- **Guests**: a guest's session (only a guest name) keeps its 30 days; the guest-name release
  rule depends on it.
- **Privacy draft**: the session line now says "after 7 days without use".

## Piece 3 — Link previews in direct messages

- **While writing**: the sender's browser asks for a preview of the draft's first https link, a
  moment after typing stops (`useDirectLinkPreview`), at the new route
  `POST /api/chat/direct/preview { url }` (members only).
- **The route** (`server/src/previews/directPreview.js`):
  - **Fetches** with the existing preview fetcher (`fetchPreview` with `safeFetch`'s network
    guard, `fetchImage`). `fetchPreview` gained a parameter for how the image is kept; rooms
    keep storing it in the media folder.
  - **Answers** the title, description, site name and an optional image re-encoded by the
    server: WebP at most 320px wide and 50 KB (lower quality, then narrower, else no image),
    as a data URL.
  - **Stores nothing**: no cache row, no file, no database write.
  - **Logs nothing**: no line at all, not even a failing link's host.
  - **Records nothing about who asked**: only the per-account rate-limit counter
    (`makeWindowLimit`, the room previews' limits) counts.
- **Travels encrypted**: the card goes inside the message's ciphertext (`preview` in the
  payload). The sender sees it above the composer's field and can remove it (×). One card per
  message, the first link's.
- **Size limits raised for that small image**:
  - `CIPHERTEXT_MAX` 16,000 → 120,000 base64 characters.
  - `/api/chat/direct` gets its own 160 kB JSON parser; everything else stays at 100 kB.
- **The recipient's browser never contacts the linked site**: a received card is kept only as
  the sender's browser makes it (`safePreview`): an https link, plain text, and an image only
  as inline `data:image/webp;base64`. Anything else is dropped.
- **Account setting**: "Link previews in direct messages", account page, Privacy, on by
  default.
  - Stored in `users.dm_link_previews` (new column, added to older databases) and set through
    the existing `PUT /api/auth/privacy`, which now takes either switch (`setPrivacy` replaces
    `setShowOnline`).
  - When it is off, the browser makes no preview request at all, and the route refuses one too.
- **Privacy draft**: a paragraph on link previews in private messages.
- **Reused**: `fetchPreview`, `fetchImage`, `safeFetch`, `makeWindowLimit`, `firstHttpsLink`,
  `PreviewCard`, the composer attachment's × style, `encryptDirect` / `decryptDirect`, and the
  test helpers `previewInternet`, `storedDirect` and `mockApi`.

## Piece 4 — Encrypted files in direct messages

- **Attaching**: members attach a file of any type with the composer's usual "Attach file"
  (`ComposerUpload`, which now takes the upload way and the accepted types). The room uploads'
  limits apply: 10 MB per file (plus the encryption's few bytes), one daily quota of 50 MB
  together with room uploads, the `chatUpload` rate limit.
- **Encrypted in the sender's browser** (`encryptFile` in `shared/crypto.js`): a fresh random
  key per file, libsodium `crypto_secretstream_xchacha20poly1305` in 64 KB chunks. Every chunk
  is authenticated, and the last one is tagged final, so a file cut short does not open either.
- **The server stores ciphertext only**: `POST /api/chat/direct/:id/files`, under a generated
  name in `MEDIA_DIR/direct/`, never public (the `/media` mount serves only library, preview
  and event-image names). The file's key, name, type and size travel only inside the encrypted
  message. The message names the upload id, so the server can link the two for access and
  clean-up; only the uploader's own upload for that partner, sent once.
- **Served to the two members only**: `GET /api/chat/direct/files/:fileId`; anyone else gets
  404, guests 401, and a pending upload goes to its uploader only. Always as plain data, a
  download, sandboxed.
- **The recipient's browser decrypts it** (`DirectFile.jsx`). **Safety rule**: only PNG, JPEG,
  GIF and WebP, recognised by their first bytes after decryption (`rasterType`), are shown, as
  an object URL in an `img`. The stated name and type do not count. SVG, HTML and everything
  else is offered only as a download, as plain data.
- **No server-side thumbnails or content checks**: the server enforces size and participant
  access only.
- **Reports**: reporting a message with a file (the existing release flow) also shares that
  file, decrypted in the reporter's browser as the text is
  (`POST .../:id/reports/:reportId/files/:messageId`, the reporter's own report and a shared
  message only, once). Moderators get it as a download only, audited
  (`chat.direct_report_file_view`); Admin → Chat shows "Download <name>" beside the copy. The
  report answer now names its `reportId`.
- **Deletion**: a file lives as long as its message. Direct messages have no delete action of
  their own, so the deletions are retention and an account's deletion. Either way the retention
  job deletes the row and the file on disk, and also any file in `direct/` or
  `direct-reports/` that no row names. A report's shared file goes with the report's copies.
- **Docs**: CHAT.md, ARCHITECTURE.md, and the privacy draft (files in private messages are
  end-to-end encrypted).
- **Found on the way**: a picture that decrypts after the newer messages below it arrived did
  not keep a reader at the end of the list. `useScrollPin` watched only the newest message, and
  a late scroll event from its own jump could unpin the reader. Now every message is watched,
  and only scrolling up unpins. This helps rooms too.
- **Reused**: the upload limits, `bytesUploadedSince`, `saveMediaFile` / `deleteMediaFile`,
  `partnerHandlers`, `makeLimiter`, `recordAudit`, the retention job, `fileSize`, the composer
  attachment display, and the test helpers `memberWithKey`, `sendDirect` (now with extra body
  fields), `readDirect`, `storedDirect` and `mockApi` (now able to answer binary data).

## Piece 5 — Unlock a new device from a logged-in one

- **Where**: on a device without the private key, the unlock section offers **Confirm on
  another device** (`UnlockPanel` → `DeviceUnlock.jsx`), besides the password and the recovery
  code.
- **The new device** makes a one-time key pair and sends its public key
  (`POST /api/keys/handover`). It shows a 6-digit code computed from that public key
  (`handoverCode`: BLAKE2b of the key). The other device computes the same code from the key it
  received, so a key swapped on the way shows a different code.
- **The request** (`server/src/keys/handover.js`):
  - valid 5 minutes, one at a time per account (`409 request_pending`), 10 an hour per account;
  - kept in the server's memory only, not in the database;
  - relayed as a personal event (`keyRequest`) over the existing live connection to the
    account's own open pages, never anyone else's.
- **The unlocked device** (`DeviceRequestPrompt.jsx`, in the layout for members) shows "A new
  device wants access to your direct messages — code 123 456. Is this you?" with Confirm /
  Reject. Only a page where the key is unlocked asks; it closes by itself when the request
  expires.
  - **Confirm** seals the private key to the one-time key (`crypto_box_seal`, `sealForDevice`).
    The server takes exactly an 80-byte sealed box and nothing else, so it never holds the key
    unsealed.
  - **Reject** sends nothing of the key.
- **Delivery**: the new device asks every 2 seconds (its own session only) and gets the box
  once; then the server deletes it. The new device opens the box, checks that the key belongs to
  the account's public key, and keeps it like a key its password opened (`fromOtherDevice`).
- **Nothing happens** on a wrong, rejected or expired request.
- **Audit**: request, confirm and reject (`keys.handover_*`), never with a key.
- **Found while taking the screenshots**: a rejected request kept blocking a new one until it
  expired, because the asking device never came back for the answer. Now only a request still
  waiting blocks another; a test covers it.
- **Docs**: AUTH.md ("Unlock on another device", rate-limit table), CHAT.md (keys section).
- **Reused**: `newKeyPair`, `publicKeyOf`, libsodium through `shared/crypto.js`, the personal
  events (`notify.member` → `usePersonalEvents`), `publicKeyField` / `exactBytes`,
  `recordAudit`, `makeLimiter`, the modal dialog style, `unlocked()` in `KeyContext`, and the
  test helpers `listeningChat` / `connect` / `logIn` / `memberWithKey` / `keyServer` /
  `memoryDeviceKey` / `FakeSocket`.

## Piece 6 — System notifications (while the site is open)

- **What**:
  - a mention of the member in a room they can read: "<name> mentioned you in <room>: <first
    80 characters>";
  - a new direct message: "New message from <name>", never its text.
- **The server**:
  - sends a personal `mention` event to each mentioned member's pages, with the author, the
    room and the first 80 characters; only members the mention counts for, who may read the
    room;
  - adds the sender's name to the existing `direct` event; the message itself stays ciphertext.
- **When** (`client/src/notify/`): only when no tab of the site is visible at that moment, and
  one notification per event across tabs.
  - Each tab notes its own visibility in browser storage, renewed while visible, so a closed
    tab's note fades within 15 seconds.
  - The first tab to claim an event shows it, like the call notices; the notification's tag
    also lets the browser replace a double.
  - Clicking focuses the site and opens the room (`/chat?room=`) or the conversation
    (`/chat?direct=`). The chat page now follows those two parameters.
- **Permission**: asked only when the member presses **Turn on notifications**, on the account
  page or in the chat menu ("…" on the chat page and in the drawer, members only); never on page
  load. Allowing it while both switches are off turns both on. If the browser blocks
  notifications, the account page explains how to allow them, and the chat menu leads there.
- **Account setting**: switches for mentions and for direct messages, off until turned on
  (`users.notify_mentions`, `notify_direct`, `PUT /api/auth/notifications`). The switch setter
  is shared with the privacy switches (`setSwitches`, formerly `setPrivacy`).
- **No web push**: with no tab of the site open there are no notifications. Recorded in CHAT.md
  and in backlog part one: "Notifications when the browser is closed (web push) — not built".
- **Reused**: the personal events (`usePersonalEvents`, `hub.sendToUser`), the call notices'

## Piece 7 — Call recording (video and audio)

- **How**: LiveKit Egress room composite to MP4 (`startRecording` / `stopRecording` in
  `server/src/calls/service.js`).
  - **Encoding**: 1280 x 720, 15 frames a second, H.264 Main with the video capped at 1,000
    kbit/s; AAC 64 kbit/s at 48 kHz.
  - **Layout**: LiveKit's `speaker` layout, so a shared screen or a camera is large when there
    is one, and the speakers' tiles otherwise.
- **Configuration**: two new config keys, `CALLS_RECORDINGS_DIR` (the site's folder; unset
  means the feature is off and the button hidden) and `CALLS_EGRESS_OUTPUT_DIR` (the same
  folder as the egress container sees it).
  - In production the folder is `/data/media/recordings`, inside the site's data volume, which
    git ignores (`data/`). Backups copy the media folder whole, so they include the recordings.
  - The public `/media` route never serves it; only the call routes play it.
- **Who**: only organisers and admins start and stop a recording, on a live call (audited).
  Ending the call stops it.
- **Notice, always**:
  - **The room's metadata says it runs** (`roomState.js`, which now builds spotlight and
    recording together), so everyone in the call sees a red "Recording".
  - **The start**: when a recording starts, everyone in the call gets the banner "This call is
    now being recorded".
  - **Joining**: anyone joining while it runs must first confirm "I understand this call is
    being recorded". The server gives no token without `recordingConsent: true`, so nothing
    connects without the yes.
  - **Sending**: someone who joined before it started is asked the same before turning on the
    microphone, camera or a screen share, for example when moved onto the stage.
  - **"Being recorded"**: the Calls page and the call page say it on a call while its
    recording runs.
- **Afterwards**: the call's page lists the recordings with date, length and a player, for
  the same audience as the call. Only finished ones play, with range requests so the player
  can seek. Organisers and admins delete one, file and row; nothing is deleted automatically.
- **Deployment**:
  - `deploy/calls/docker-compose.recording.yml` (new, optional) adds the egress (v1.15.0) and
    Redis (7.4.11 on 127.0.0.1), both pinned by digest, and gives LiveKit `REDIS_HOST`.
  - `deploy/calls/.env.example` gains three variables for it.
  - CI validates the combined compose config.
  - DEPLOYMENT.md has the setup, the backups, and the size: at most about 480 MB per recorded
    hour; measured with a moving test camera, about 270 MB.
  - The site's own compose needed no change: the site's settings go into `site.env`.
- **Privacy draft**: a "Call recordings" section (what is recorded, who can watch, deletion,
  backups), with [TO BE FILLED BY OWNER] for the legal basis, the keeping period and how to
  ask for deletion. The call paragraph no longer says calls are never recorded.
- **Reused**: the call service door (`service.js`), `callSteps`, `recordAudit`, the spotlight's

### Part 4 — the two flaky tests

#### `client/e2e/embedForeign.spec.js`

Two causes, both in the tests; no site bug was found, so no site code changed.

- **Run again in the same run, it hung**:
  - **Cause**: the member-login helper `memberPage()` (`client/e2e/members.js`) always waited
    for the "Protect your private messages" offer. The offer comes only with the key pair, at a
    member's first login, so from the second run on it waited for nothing.
  - **Fix**: the helper asks the run's database whether the member has a key pair yet, and
    waits for the offer only then. The run's database path is now one constant
    (`E2E_DATABASE`), also used by `globalSetup.js` and `direct.spec.js` instead of their own
    copies.
- **In a full run, now and then, no popup came** (2 of the night's full verifies; in today's
  checks 1 of 14 full browser runs):
  - **What a trace-free failure still shows**: only the wait for the popup was pending at the
    time-out, not the click, so the click had completed without reaching "Log in".
  - **Cause**: the test put the chat where no visitor could see it. `frameOf`
    (`client/e2e/frames.js`) appended the iframe after the site's own page, whose body never
    scrolls (`styles/base.css`). A temporary diagnosis measured it in every run: the chat began
    at y = 720 in a 720-pixel window, and the click needed Playwright to scroll that body by
    398 pixels first. Meanwhile the host page, the live site, kept changing with what the
    parallel tests do (live calls, messages in General). Alone, nothing changes, and it passed.
  - **Fix**: `frameOf` shows the chat in view, fixed in the host page's top-left corner above
    the page, as a game site would. Measured: the chat at y = 0, "Log in" at y = 16, the click
    point already on the chat, no scrolling at all.
  - **Not proven by a captured failure**: 13 further full runs with traces and the diagnosis
    did not fail once, so the exact moment the click missed was not caught. The fix removes
    what every run depended on (a scroll of a page that does not scroll, under a page that
    changes).

  - The read limit per address (1,200 a minute): a temporary log line in the limiter showed no
