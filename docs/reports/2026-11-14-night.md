## Piece 2 — game results on member profiles (website side)

Done. A member's profile shows one card per embedded game that answers: up to four values the
game names itself, "Last played <date>" and "Open <game>" (`/games/<slug>`). Signed-in members
only (the profile routes' own check). "Show my game results" in the account page's Profile
section (on by default) hides the cards; while it is off the games are not even asked. The
contract for the game projects is docs/GAME-INTEGRATION.md, section 7: `GET
<local origin>/games/<slug>/api/website/member-summary?user=<id>` with `X-Games-Sync-Token`,
at most 4096 bytes, 1 to 4 values (label up to 24 characters, value a whole number or up to
16), `{"noData": true}` or 404 for "no data", 1.5 s timeout, answers kept 5 minutes (failures
1). The cards load in a request of their own, so the profile never waits for a game.

- **Reused**: the games' sync token (`GAMES_SYNC_TOKEN`, the feed's; no new secret), the
  profile routes' `shown` check and `profileEdit` limit, `addMissingColumns`, `formatDate`, the
  site's switch markup (`form-check`, as the privacy switches).
- **Smaller options taken**: the website reaches a game at an origin set per game,
  `GAMES_LOCAL_ORIGINS` (in `site.env`; `.env.example` lists it). No installer question and no
  change to `docker-compose.yml` tonight. The card's link is the website's own `/games/<slug>`,
  not an address the game sends. A game's request failing is not logged.
- **Needs the owner's word**: in production the site runs in its container, where
  `127.0.0.1` is the container itself. To reach a game on the host, the site service needs
  `extra_hosts: host.docker.internal:host-gateway` (the Caddy service has it already) and the
  game a port the container can reach; the installer could then ask for each game's origin.
  Until then no game is asked on the live site.
